   OAuth Brokered Authorization: Grant Custody for Short-Lived Client
                               Instances
             draft-sweeney-oauth-brokered-authorization-00

Abstract

   An OAuth client identifier names a registration.  It does not name
   the running instance that presents a token.  Where one registered
   client runs as many short-lived instances, as agent platforms do,
   work now in progress binds refresh tokens to the instance.  Where a
   refresh token is bound to the instance, an authorization that a user
   gave through one instance ends with that instance, and no
   specification says how the next instance comes to act under it.

   This document specifies one answer.  A broker is the single, durable
   OAuth client of an upstream resource.  It holds the grant and the
   credential for that resource and makes each request itself.  A
   resource owner authorizes a registered client to use that grant
   through the broker, and the authorization server records the
   authorization against the client and not against any instance.  Each
   instance obtains a short-lived, sender-constrained access token for
   the broker with the client credentials grant.  An instance never
   holds a grant, a refresh token, or the upstream credential, and no
   instance is registered anywhere.  This document defines the
   authorization details type that carries this authority, the checks
   the broker makes before it acts, and one error code.

1.  Introduction

1.1.  The Client, the Instance, and the Grant

   [OAUTH21] defines a client as an application that makes protected
   resource requests on behalf of a resource owner, and a client
   identifier as a string that represents the registration information
   the client provided.  It does not say whether a registration stands
   for a piece of software, a deployment of it, or one running process.
   [RFC7591] named the difference in 2015, defining a client instance as
   a deployed instance of a piece of client software, but nothing in the
   core framework depends on it.






Sweeney                    Expires 24 May 2027                  [Page 3]

Internet-Draft        OAuth Brokered Authorization         November 2026


   For a web application with one deployment, the difference did not
   matter.  For agent platforms it does.  One registered client runs as
   many concurrent instances, each lives for a task or a session, and
   some start further instances.

   Work in progress identifies the instance.  [ATTEST] authenticates a
   client instance by a key the instance generated and an attestation
   over that key, and requires a refresh token to be bound to the client
   instance and not only to the client.  [CLIENT-INSTANCE-ID] adds an
   instance identifier that survives a key change, and has the
   authorization server record the instance at grant time and require
   the same instance at refresh.  [AIMS] treats an agent as a workload
   that acts as an OAuth client and is named in the client_id claim.

   These are sound, and they sharpen a question that OAuth has left to
   authorization server policy: where does a grant live when the
   instance that obtained it is gone?  If the grant is reachable only
   through a refresh token bound to an instance, it ends with the
   instance, and the resource owner is asked again for each new one.  If
   every instance is instead registered as a client of its own, each
   needs its own registration and its own consent at every authorization
   server it touches, and the resource owner can no longer tell what was
   approved.

   A third course exists.  A confidential client's backend can keep a
   refresh token that is bound to the client and not to an instance
   (Section 4.3 of [OAUTH21]), and [ATTEST] lets a profile bind refresh
   tokens to something other than the instance key (its Section 13).
   That keeps a long-lived credential in the client's own systems.  This
   document keeps the grant at the authorization server.  Of the grant,
   the client keeps only an identifier, which is of no use without
   client authentication (Section 7.2).

1.2.  The Answer Given Here

   This document answers the question for resources that are reached
   through a broker, by fixing what each party holds:

   A resource owner authorizes the logical client once.  Any instance
   that authenticates as that client can then obtain an access token for
   the broker with the client credentials grant, which Section 4.2 of
   [OAUTH21] permits for the resources of another resource owner when
   that has been previously arranged with the authorization server.  The
   brokered authorization is that arrangement.  When an instance ends,
   its tokens expire and nothing else changes.  The upstream resource
   sees one client and needs no change, which matters because many
   upstream resources accept only a bearer token or a static API key and
   will not adopt instance-aware mechanisms.

1.3.  Existing Work

   A component that holds a credential and makes each request itself is
   not new.  Section 9.1 of [OAUTH21] and Section 6.1 of [RFC10017]
   describe it for browser applications as the Backend for Frontend, and
   [RFC10017] ranks it above the token-mediating backend of its
   Section 6.2, which passes the access token to the application.






Sweeney                    Expires 24 May 2027                  [Page 5]

Internet-Draft        OAuth Brokered Authorization         November 2026


   Two pieces of the mechanism have earlier forms.  Grant Management for
   OAuth 2.0 [GRANT-MGMT] makes a grant an object at the authorization
   server, named by a grant_id that a client presents in later
   authorization requests.  [MISSION-RA] defines an authorization
   details type with path-prefix matching at a segment boundary (its
   Section 4), a subset rule (its Section 5), and enforcement where the
   token is presented (its Section 7).

   This document defines a type of its own, and not a use of that one,
   for three reasons.  An entry of [MISSION-RA] is enforced by the
   resource server that the token is presented to (its Section 7), and
   its actions are identifiers that the serving resource defines (its
   Section 3).  The entries defined here are enforced by a broker in
   front of a resource that implements nothing, and are stated in terms
   that resource already has: HTTP methods and paths.  They name the
   upstream grant that the broker is to use, and [MISSION-RA] gives no
   authority to an entry with a member it does not define (its
   Section 7).  And they are redeemed at the token endpoint with client
   authentication alone.  A broker could also be the enforcement point
   for entries of [MISSION-RA]; that is not defined here (Section 11).

1.4.  What This Document Defines

   *  The brokered authorization: what it records, how it is made, and
      how a client instance obtains an access token under it
      (Section 4).

   *  An authorization details type [RFC9396] that carries the
      operations a token permits and the upstream grant it uses
      (Section 5).

   *  What the broker checks before it acts, what it never does with the
      upstream credential, and one new error code (Section 6).

   This document does not define how an instance is identified or
   attested.  It works with any client authentication method that proves
   possession of a key held by the instance, and it carries instance
   context where the authorization server has it (Section 4.4).

   Apart from the path computation, the custody rules, and the upstream
   grant error of Section 6, this document does not define how the
   broker builds the request it sends upstream or how it filters the
   response.  Those rules decide whether the arrangement is safe in
   practice, and Section 6.9 lists what they have to cover.

   It defines no delegation chain between agents, no receipt or audit
   record, and no limit accounting.  It does not define how the broker
   comes to hold an upstream credential.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This document uses "authorization server", "resource server",
   "protected resource", "client", "resource owner", and "access token"
   as defined in [OAUTH21].

   Logical client:  The OAuth client identified by a client identifier
      at the broker's authorization server.  Many client instances can
      authenticate as it.  The term is taken from [CLIENT-INSTANCE-ID].

   Client instance:  One deployed, running instance of the logical
      client's software, as in [RFC7591] and [ATTEST].  It holds a key
      that no other instance holds.

   Upstream resource:  A protected resource that the broker calls.  It
      is identified by one origin and one path prefix.  Where an
      upstream service gives each account its own origin, the origin can
      be fixed per upstream grant (Section 6.1).

   Upstream credential:  What the upstream resource accepts as proof of
      authority and the broker holds: a bearer access token, together
      with any refresh token from which it is renewed, or a static API
      key.  Passwords and private keys are not covered by this document.

   Derived credential:  Anything obtained from the upstream resource
      that lets its holder act at the upstream resource without the
      broker.  Examples are a newly issued API key or token, a session
      cookie, and a URL that carries its own authorization.

   Upstream grant:  The authority that one resource owner has given the
      broker at one upstream resource, of which the upstream credential
      is the evidence.  The broker records each upstream grant with the
      resource owner who made it.  The authorization server assigns an
      identifier for it to each logical client (Section 5).

   Brokered authorization:  A record at the broker's authorization
      server that a resource owner permits a logical client to have the
      broker perform stated operations under one upstream grant
      (Section 4).

   Broker:  A server that holds upstream credentials and uses them to




Sweeney                    Expires 24 May 2027                  [Page 7]

Internet-Draft        OAuth Brokered Authorization         November 2026


      make requests to upstream resources for client instances, under
      the rules of this document.  It is an HTTP gateway (Section 3.7 of
      [RFC9110]).  Together with its authorization server it is one
      party.

   Broker resource:  A protected resource that the broker exposes and
      that stands for exactly one upstream resource.

   Operation:  One kind of request that a broker resource offers,
      defined in the broker's configuration (Section 6.1).

   Release:  Any act by which a client instance comes to hold an
      upstream credential or a derived credential.

   Extends at a segment boundary:  A path P extends a path Q at a
      segment boundary when P begins with Q and either Q ends with "/"
      or the next character of P after Q is "/".

   The word "broker" is also used elsewhere for an authorization server
   that federates to another authorization server.  That is a different
   role and is not meant here.

3.  Model and Assumptions

    +-----------+  (1) client credentials  +---------------+
    |           |------------------------->| Broker's      |
    | Client    |<-------------------------| authorization |
    | instance  |  (2) access token        | server        |
    |           |                          +---------------+
    |           |  (3) request             +--------+  (4)  +----------+
    |           |------------------------->|        |------>|          |
    |           |<-------------------------| Broker |<------| Upstream |
    +-----------+  (6) response            +--------+  (5)  | resource |
                                                            +----------+

   Beforehand, the resource owner has authorized the broker at the
   upstream resource (the upstream grant), and has authorized the
   logical client at the broker's authorization server (the brokered
   authorization).

   1.  A client instance authenticates as the logical client and asks
       for an access token with the client credentials grant, naming the
       broker resource, the upstream grant, and the operations it needs.

   2.  The authorization server checks the request against the brokered
       authorization and issues a short-lived access token bound to the
       instance's key.




Sweeney                    Expires 24 May 2027                  [Page 8]

Internet-Draft        OAuth Brokered Authorization         November 2026


   3.  The instance sends an HTTP request to the broker resource with
       the token and proof of possession.

   4.  The broker validates the token and the proof, matches the request
       to a configured operation, checks that the token permits it, and
       sends the corresponding request upstream with the credential of
       the upstream grant the token names.

   5.  The upstream resource answers the broker.

   6.  The broker returns the answer.

   This document rests on the following assumptions.  Where one does not
   hold, the properties claimed in Section 7 do not hold either.

   *  The broker and its authorization server are operated by one party
      and share the record of upstream grants and brokered
      authorizations.

   *  The authorization server knows which resource owner made each
      upstream grant.

   *  Every instance of a logical client is trusted with every brokered
      authorization made to that client (Section 7.2).

   *  A client instance's key cannot be exported by the part of the
      instance that an attacker can influence, and is not copied to
      another instance (Section 7.3).

   *  One upstream credential stands for one resource owner
      (Section 7.6).

   *  The broker's operator knows the upstream resource well enough to
      list the operations that are safe to offer (Section 7.4).

   *  The upstream resource reads a path as [RFC3986] describes.  It
      does not fold case, give meaning to path parameters, or decode a
      second time.

4.  Brokered Authorizations

4.1.  The Record

   A brokered authorization records:

   *  the resource owner who made it;

   *  the logical client it was made to;



Sweeney                    Expires 24 May 2027                  [Page 9]

Internet-Draft        OAuth Brokered Authorization         November 2026


   *  one broker resource and one upstream grant at that broker
      resource, made by the same resource owner;

   *  the operations permitted, as in Section 5;

   *  the issuer identifier of the authorization server that recorded
      it;

   *  when it ends, if it has an end.

   There is at most one brokered authorization for a given logical
   client and upstream grant.

   A brokered authorization is not bound to a client instance, to a key,
   or to a refresh token.  It persists until it ends or the resource
   owner withdraws it.

   The authorization server MUST NOT record a brokered authorization
   unless the resource owner who made the upstream grant, or a party
   entitled under the deployment's policy to act for that resource
   owner, has approved it for that logical client.  Authenticating the
   client is not enough.

4.2.  Making a Brokered Authorization

   A resource owner makes a brokered authorization through the
   authorization code grant (Section 4.1 of [OAUTH21]) at the broker's
   authorization server.  The authorization request MUST be a pushed
   authorization request [RFC9126] in which the client instance
   authenticates as in Section 4.3.  The authorization server MUST
   reject a request for this type that was not pushed.  The request
   carries an authorization_details parameter [RFC9396] with exactly one
   object of the type defined in Section 5.

   The authorization server shows the resource owner the logical client,
   the broker resource, the upstream resource it stands for, and the
   operations requested.  It MUST make plain that:

   *  any running instance of the client can use the authorization,
      without further approval, until it ends or is withdrawn;

   *  a path includes everything beneath it, including operations that
      the broker adds there later;

   *  where an operation requested hands the instance a URL that carries
      its own authorization (Section 7.4), that it does.





Sweeney                    Expires 24 May 2027                 [Page 10]

Internet-Draft        OAuth Brokered Authorization         November 2026


   Where the resource owner has more than one upstream grant at that
   broker resource, the authorization server has the resource owner
   choose one.  Where the resource owner has none, the authorization
   server either has one made in the same interaction or returns the
   access_denied error.

   The brokered authorization is recorded when the authorization code is
   redeemed, and not before.  It replaces any earlier brokered
   authorization for the same logical client and upstream grant.  The
   authorization server adds the upstream grant identifier to the
   object, as Section 7.1 of [RFC9396] allows a type to provide.

   Where the authorization server did not itself register the client, as
   with a client identifier that is a URL under the client's control,
   the brokered authorization MUST have an end.

   The token response contains the authorization_details as recorded,
   including the upstream grant identifier.  The access token it returns
   meets the requirements of Section 4.3.  The authorization server MUST
   NOT issue a refresh token: an instance that needs a further access
   token obtains it under Section 4.3.

   An authorization server MAY provide other ways to make a brokered
   authorization.  Those are outside this document.  The rule in
   Section 4.1 applies to all of them.

4.3.  Obtaining an Access Token

   A client instance obtains an access token for a broker resource with
   the client credentials grant (Section 4.2 of [OAUTH21]).  The token
   request:

   *  MUST authenticate the instance as the logical client with a method
      that proves possession of a private key held by that instance,
      such as [ATTEST] or mutual TLS [RFC8705].  A symmetric client
      secret MUST NOT be accepted;

   *  MUST carry an authorization_details parameter with exactly one
      object of the type defined in Section 5, including its
      upstream_grant member;

   *  MUST present, as the key the access token is to be bound to, the
      key with which the instance authenticates.  The authorization
      server MUST refuse any other.  With [ATTEST] that is its combined
      mode, in which the DPoP key is the Client Instance Key (its
      Section 5.2).  With mutual TLS it is the client certificate.





Sweeney                    Expires 24 May 2027                 [Page 11]

Internet-Draft        OAuth Brokered Authorization         November 2026


   The logical client MUST be a confidential client (Section 2.1 of
   [OAUTH21]), which Section 4.2 of [OAUTH21] requires for this grant.

   The authorization server MUST issue an access token only if a
   brokered authorization exists for that logical client, that broker
   resource, and that upstream grant, has not ended or been withdrawn,
   and covers the object requested (Section 5.2).  Otherwise it responds
   with the invalid_authorization_details error of [RFC9396].  The
   response MUST NOT reveal whether the upstream grant identifier
   exists.

   The access token:

   *  MUST be sender-constrained to the key with which the instance
      authenticated;

   *  MUST have as its audience the resource identifier [RFC8707] of
      that one broker resource;

   *  MUST convey, in its authorization_details claim or in the
      introspection response (Section 9 of [RFC9396]), exactly one
      object of the type defined in Section 5, which names that broker
      resource and that upstream grant and contains no operation beyond
      those requested;

   *  where it is a JWT access token [RFC9068], MUST carry the client
      identifier in both sub and client_id.  The resource owner is
      identified only through upstream_grant;

   *  MUST NOT be accompanied by a refresh token.

   The lifetime of an access token SHOULD NOT exceed 300 seconds.  Where
   the broker relies on token expiry to apply a withdrawal, the lifetime
   MUST NOT exceed the limit stated under Section 6.6.

   A brokered_access object MUST NOT be conveyed in an access token
   issued in any other way than under Section 4.2 or this section.

4.4.  Instance Context

   Where the authorization server has instance context for the
   authenticated instance, such as the client_instance claim of
   [CLIENT-INSTANCE-ID] (its Section 7.1), it SHOULD convey it with the
   access token.

   Instance context grants no authority under this document.  The broker
   uses the key the token is bound to as the identity of the instance
   when it refuses an instance (Section 6.6).

5.  The Authorization Details Type

   This document defines the authorization details type brokered_access.
   An object of this type has the following members.

   type:  REQUIRED.  The string brokered_access.

   locations:  REQUIRED.  An array with exactly one element, the
      resource identifier of a broker resource.

   upstream_grant:  The upstream grant identifier.  OPTIONAL in an
      authorization request, where the authorization server supplies it
      (Section 4.2).  REQUIRED in a token request under Section 4.3, in
      a token response, and in what is conveyed to the broker.  The
      value is an opaque string assigned by the broker's authorization
      server.  It confers nothing on a party that cannot authenticate as
      the logical client.  Among instances of one logical client it is
      all that separates one resource owner's authorization from
      another's.  It MUST contain at least 128 bits of randomness, MUST
      be specific to one logical client, and MUST NOT be reused for a
      different upstream grant.

   operations:  REQUIRED.  A non-empty array of objects, each with these



Sweeney                    Expires 24 May 2027                 [Page 13]

Internet-Draft        OAuth Brokered Authorization         November 2026


      members:

      methods:  REQUIRED.  A non-empty array of HTTP method names, as
         they appear in a request.  HEAD MUST NOT appear; an entry that
         lists GET permits HEAD.

      path:  REQUIRED.  A path relative to the broker resource,
         beginning with "/".  The value "/" stands for the whole broker
         resource.  The value MUST be in the form that Section 6.2
         produces: no dot-segments, no backslash, no %2F or %5C, and
         normalized as that section describes.

      names:  OPTIONAL.  A non-empty array of operation names
         (Section 6.1).  When present, the entry applies only to
         configured operations with one of those names.

   An object MUST NOT contain the actions, datatypes, identifier, or
   privileges members of Section 2.2 of [RFC9396].  As Section 5 of
   [RFC9396] requires, the authorization server refuses an object with
   an unknown member or a member that does not conform.

   For example:

   {
     "type": "brokered_access",
     "locations": ["https://broker.example/tracker"],
     "upstream_grant": "ug_5Yc1r0mB7tQk2VxN9aLd3w",
     "operations": [
       { "methods": ["GET"], "path": "/projects/42/issues" },
       { "methods": ["POST"], "path": "/projects/42/issues",
         "names": ["issue.comment"] }
     ]
   }

5.1.  When an Entry Permits a Request

   An entry of operations permits a request that has been matched to a
   configured operation (Section 6.1) when all of the following hold:

   1.  the request method is in methods, where a HEAD request is treated
       as GET;

   2.  the request path, relative to the broker resource and as computed
       in Section 6.2, equals path or extends it at a segment boundary;

   3.  if the entry has names, the configured operation has a name and
       that name is in names;




Sweeney                    Expires 24 May 2027                 [Page 14]

Internet-Draft        OAuth Brokered Authorization         November 2026


   4.  if the configured operation is one that the upstream resource
       determines from request content (Section 6.1), the entry has
       names.

   An object permits a request when at least one of its entries does.
   Comparison of methods, paths, and names is by exact string.

5.2.  When One Object Covers Another

   An object A covers an object B when both have the same single
   locations value and the same upstream_grant, and for every entry of B
   there is an entry of A such that:

   1.  every method of the entry of B is in the methods of the entry of
       A;

   2.  the path of the entry of B equals the path of the entry of A or
       extends it at a segment boundary;

   3.  if the entry of A has names, the entry of B has names and every
       name in it is in the names of the entry of A.  If the entry of A
       has no names, the entry of B has none.

   The authorization server issues a token under Section 4.3 only when
   the brokered authorization covers the object requested.

5.3.  Metadata

   A broker resource that publishes protected resource metadata
   [RFC9728] includes brokered_access in
   authorization_details_types_supported.  The broker's authorization
   server includes it in its own authorization_details_types_supported
   (Section 10 of [RFC9396]).

   This document does not define how a client learns the operation names
   a broker resource uses (Section 11).

6.  The Broker

6.1.  Broker Resources and Operations

   Each broker resource MUST correspond to exactly one upstream
   resource.  The correspondence, and the operations the broker resource
   offers, are fixed in the broker's configuration and MUST NOT depend
   on anything in a request.  The one exception is the origin of the
   upstream resource, which can be fixed per upstream grant when that
   grant is made.




Sweeney                    Expires 24 May 2027                 [Page 15]

Internet-Draft        OAuth Brokered Authorization         November 2026


   An operation is defined by:

   *  a method.  An operation MUST NOT be configured with the method
      HEAD.  A HEAD request matches an operation whose method is GET;

   *  a path relative to the broker resource, or a path pattern in which
      each variable matches exactly one non-empty segment;

   *  the names of the query parameters it accepts.  The broker parses
      the query as name and value pairs separated by "&" only;

   *  optionally, a name, which is a string unique within the broker
      resource.  An operation name MUST NOT be reassigned to a different
      operation;

   *  where the upstream resource determines what is done from the
      request content and not from the method and path alone, a name and
      the constraints on content that identify what is permitted.
      Examples are a single endpoint that accepts both queries and
      mutations, a remote procedure call named in the content, and a
      batch of calls in one request.

   An operation's query parameter names MUST NOT include one that the
   upstream resource accepts as a credential or uses to choose the
   account, tenant, or user that a request acts as.

   An operation MUST NOT be configured where the upstream resource lets
   a query parameter, a request field, or request content override the
   method or the target, unless the operation's definition excludes that
   override.

   An operation MUST NOT be configured with the method CONNECT or TRACE.

6.2.  The Request Path

   The broker resource's path prefix is the path of its resource
   identifier, or "/" if that is empty.  The broker computes the path of
   a request relative to the broker resource as follows.

   1.  The broker MUST reject, with a 400 (Bad Request) status code, a
       path that contains a backslash or the percent-encoded octets %2F
       or %5C in either case.









Sweeney                    Expires 24 May 2027                 [Page 16]

Internet-Draft        OAuth Brokered Authorization         November 2026


   2.  The broker applies the normalizations of Sections 6.2.2.1 and
       6.2.2.2 of [RFC3986] once.  It MUST then reject, with a 400 (Bad
       Request) status code, a path with a segment that contains ";" and
       that, once everything from its first ";" is removed, is "." or
       "..".  It then applies the remove_dot_segments procedure of
       Section 5.2.4 of [RFC3986].

   3.  The result MUST equal the broker resource's path prefix or extend
       it at a segment boundary.  Otherwise the broker MUST reject the
       request with a 400 (Bad Request) status code.

   4.  The broker removes the broker resource's path prefix, without any
       trailing "/", from the result.  What remains, or "/" if nothing
       remains, is the path relative to the broker resource.

   That relative path is the one matched against operations, the one
   tested in Section 5.1, and the one from which the path sent upstream
   is formed.  The broker MUST NOT use any other form of the path.

   A broker MUST NOT provide a broker resource whose upstream target is
   chosen by the client instance.

6.3.  Access Tokens

   An access token presented at a broker resource MUST be sender-
   constrained, with DPoP [RFC9449] or with mutual TLS [RFC8705].
   Section 1.4.3 of [OAUTH21] and [RFC9700] recommend sender-constrained
   access tokens.  This document requires them, because a bearer token
   for a broker resource would be a copyable credential for everything
   the broker can do with it.  The broker MUST reject, with a 401
   (Unauthorized) status code and the invalid_token error, an access
   token that carries no key confirmation.

   The broker MUST reject an access token unless its audience is the
   resource identifier of the broker resource at which it is presented,
   compared as an exact string.

   The broker MUST reject an access token unless it conveys exactly one
   brokered_access object whose locations value is that same resource
   identifier.

   The broker validates the token and the proof of possession as any
   protected resource does, and returns the errors defined in
   Section 5.3 of [OAUTH21] and Section 7.1 of [RFC9449].  Where mutual
   TLS is used and TLS is terminated in front of the broker, Section 6.5
   of [RFC8705] applies.





Sweeney                    Expires 24 May 2027                 [Page 17]

Internet-Draft        OAuth Brokered Authorization         November 2026


6.4.  Deciding Whether to Act

   Before it sends anything upstream, the broker MUST establish that:

   1.  the request matches exactly one configured operation: its method,
       its path, every query parameter name, and any content constraint
       (Section 6.1); and

   2.  the brokered_access object the token conveys permits the request
       (Section 5.1).

   Where the request matches no operation, the broker responds with a
   404 (Not Found) status code, or 405 (Method Not Allowed) where the
   path matches and the method does not.  Where it matches more than
   one, the configuration is at fault and the broker responds with a 500
   (Internal Server Error) status code.  Where the object does not
   permit the request, the broker responds with a 403 (Forbidden) status
   code and the insufficient_scope error.  In none of these cases is
   anything sent upstream.

6.5.  Selecting the Upstream Grant

   The broker resource is determined by the request target.  The
   upstream grant is the one named by upstream_grant in the
   brokered_access object the validated access token conveys, and by
   nothing else.

   The broker MUST NOT take the upstream grant, the resource owner, or
   any other input to the choice of upstream credential from the request
   target, from a request field, from request content, or from the
   token's subject.

   The broker MUST reject the request if the upstream grant named does
   not belong to the broker resource at which the token is presented.

   The broker MUST reject a token unless it was issued by the issuer
   recorded with the brokered authorization that the upstream grant
   identifier names.

6.6.  Withdrawal

   A broker that accepts a token on its signature and expiry alone will
   keep accepting it after the brokered authorization behind it has been
   withdrawn, until the token expires.  Holding the upstream credential
   at the broker does not change that.






Sweeney                    Expires 24 May 2027                 [Page 18]

Internet-Draft        OAuth Brokered Authorization         November 2026


   A broker MUST apply the withdrawal of a brokered authorization, and
   the refusal of a particular instance key, to requests it receives
   after a delay no longer than a limit that the deployment states.  A
   broker that checks the current state of the brokered authorization at
   each request has a limit of zero.  A broker that relies on token
   expiry has a limit equal to the longest lifetime of the tokens it
   accepts.

   A key can be refused by the logical client or by the broker's
   operator.  How either asks is outside this document.

   The end of a client instance requires no action.  Its tokens expire.
   The brokered authorization and the upstream grant are not affected.

6.7.  The Upstream Credential Is Not Released

   The upstream grant and any upstream refresh token belong to the
   broker as the client of the upstream resource.  They are never bound
   to a client instance.

   The broker MUST NOT place an upstream credential in a response it
   generates or in a field it adds to a response.

   The broker and its authorization server MUST NOT provide an interface
   that returns an upstream credential to a client instance.

   The broker MUST send an upstream credential only to the upstream
   resource it belongs to and, where it is an OAuth credential, to the
   token endpoint of the authorization server that issued it.

   The broker MUST NOT forward to the upstream resource a header field
   received from a client instance that the upstream resource accepts as
   a credential or uses to choose the account, tenant, or user that a
   request acts as.

   The broker MUST NOT forward to a client instance a response header
   field in which the upstream resource conveys a credential or a
   challenge, such as Set-Cookie or WWW-Authenticate.  It follows that a
   WWW-Authenticate field in a response from a broker resource always
   comes from the broker.

   A component that exercises an upstream credential on one path and
   releases the same credential on another does not have the properties
   this document describes.







Sweeney                    Expires 24 May 2027                 [Page 19]

Internet-Draft        OAuth Brokered Authorization         November 2026


6.8.  Errors About the Upstream Grant

   The broker can lack a usable upstream credential: the upstream grant
   has expired or was withdrawn at the upstream resource, or the
   upstream resource refuses the credential for a reason the broker
   cannot see.  The instance's own token is not at fault and a new one
   will not help.

   When the broker has no usable upstream credential for the request, or
   the upstream resource answers 401 (Unauthorized) and the broker
   cannot obtain a credential that the upstream resource accepts, the
   broker MUST respond with a 403 (Forbidden) status code and a WWW-
   Authenticate challenge, for the scheme the instance used, whose error
   parameter is upstream_authorization_required.  It does not forward
   the upstream 401.

   HTTP/1.1 403 Forbidden
   WWW-Authenticate: DPoP error="upstream_authorization_required",
       error_description="The broker has no credential that the
       upstream resource accepts for this request."

   This error does not indicate that the access token is invalid.  An
   instance that obtains a new access token in response to it will
   receive the same error.  The remedy is for the resource owner to
   authorize the broker again at the upstream resource.

6.9.  Forwarding

   Apart from what Section 6.2, Section 6.7, and Section 6.8 require,
   how the broker builds the request it sends upstream and how it
   returns the response are outside this document.  A broker's rules for
   them have to cover at least:

   *  how the path sent upstream is formed from the relative path of
      Section 6.2;

   *  where the upstream host comes from, and that it is never taken
      from a value in a request;

   *  which request and response header fields pass, as an explicit
      list;

   *  how the query is rebuilt, so that the broker and the upstream
      resource read the same parameters;

   *  redirects, and that a credential is never sent to a redirect
      target outside the upstream resource;




Sweeney                    Expires 24 May 2027                 [Page 20]

Internet-Draft        OAuth Brokered Authorization         November 2026


   *  renewal of the upstream credential, and that the place of renewal
      never comes from an upstream response;

   *  stored responses, and that one upstream grant's response never
      answers a request under another;

   *  replay of a proof of possession, which covers the method and path
      of a request and not its query or content;

   *  what an instance can conclude when the broker fails to get a
      response, and when, if ever, a request that may have reached the
      upstream resource is sent a second time.

7.  Security Considerations

7.1.  The Broker Holds Everything

   A broker concentrates upstream credentials, often for many resource
   owners and many upstream resources.  Compromise of the broker is
   compromise of all of them.  A resource owner who uses a broker is
   trusting it with everything the upstream grant allows.  Nothing in
   this document reduces that trust.  It moves the grant and the
   credential out of every instance and into one place.

7.2.  Any Instance of the Client Can Act

   A brokered authorization is made to a logical client.  Any instance
   that can authenticate as that client and knows the upstream grant
   identifier can obtain a token under it.  That is the purpose: it is
   what lets a new instance act without asking the resource owner again.
   It is also the main exposure of this design.  An instance that serves
   one resource owner can ask for a token under another resource owner's
   brokered authorization to the same client, if it learns that
   identifier.

   Between logical clients the design does not rest on the identifier
   being unknown.  Between instances of one client it does.  The control
   is the logical client's own: whatever authenticates its instances
   decides which code runs as that client, and the client decides which
   instance is given which identifier.  A resource owner who approves a
   brokered authorization is trusting the logical client with that, as a
   user who authorizes any confidential client trusts its backend with
   the tokens of all its users.  The comparison holds only where every
   instance is as trusted as that backend.  An instance that reads
   untrusted content is not.  The credential with which an instance
   authenticates works, in effect, as a refresh token for every resource
   owner who has made a brokered authorization to that client.




Sweeney                    Expires 24 May 2027                 [Page 21]

Internet-Draft        OAuth Brokered Authorization         November 2026


   A logical client whose instances run in places it does not control,
   such as a customer's infrastructure, is a poor fit for a single
   client identifier under this document.  This document defines no way
   to restrict a brokered authorization to some instances of the client
   (Section 11).

7.3.  The Instance's Key

   Everything this document says about access tokens depends on the
   instance's key.  A key that sits in the memory or the files of the
   same process that reads untrusted content is as easy to copy as a
   bearer token.  An instance that an attacker can induce to disclose a
   bearer credential can be induced to disclose such a key.

   The arrangement is only better than a bearer credential where the key
   cannot be exported by the part of the instance that an attacker can
   influence: held in hardware, in an operating system key store, or in
   a separate process that signs proofs and does not reveal the key.
   Even then, an attacker who controls the instance can make any request
   the token permits, and can obtain further tokens under Section 4.3,
   for as long as it controls the instance.  The broker and the brokered
   authorization limit what that is.  They do not make a compromised
   instance safe.

7.4.  Operations That Return Credentials

   Custody is defeated if an instance can get a derived credential out
   of the upstream resource.  Operations that do this include:

   *  operations that create or return credentials, such as an endpoint
      that issues an API key or a personal access token for the resource
      owner's account;

   *  operations that reflect the request, including its header fields,
      in the response;

   *  operations that change where the upstream resource sends
      credentials or secrets, such as registering a webhook or a
      redirect URI that the instance controls.

   An operation of these kinds MUST NOT be configured (Section 6.1).

   An operation whose response contains a URL that carries its own
   authorization, as many download operations do, releases a derived
   credential for one object for a limited time.  It SHOULD NOT be
   configured.  Where it is, the authorization server MUST tell the
   resource owner so when the brokered authorization is made
   (Section 4.2).



Sweeney                    Expires 24 May 2027                 [Page 22]

Internet-Draft        OAuth Brokered Authorization         November 2026


   The list of operations is only as good as the operator's knowledge of
   the upstream resource.  An upstream resource can add a credential-
   returning behavior to an existing operation without notice.  Where
   the operation is determined by content, the content constraint has to
   be at least as exact as the upstream resource's own parsing.  These
   are limits of the arrangement, not of this document's wording.

7.5.  Requests That Are Not What They Seem

   The broker decides on a request and the upstream resource acts on
   one.  Any difference between how the two read the same message is a
   way around the decision.  The path computation (Section 6.2), the
   operation list (Section 6.1), and the forwarding rules a broker
   adopts (Section 6.9) each close one such difference.  They do not
   close differences in how the upstream resource parses content, and
   they do nothing about content in a response that is meant to mislead
   the instance that reads it.

   A path in a brokered_access object is a prefix.  An entry for
   "/projects/42" without names permits every configured operation at or
   beneath it with the listed methods, except one determined by request
   content.

7.6.  A Credential Shared Between Resource Owners

   Some upstream resources issue one credential for a whole
   organization.  Where a broker uses one upstream credential for
   requests made under several resource owners' authority, the upstream
   resource enforces nothing between them, and the broker's operation
   list and token checks are the only separation.  This document's rules
   do not make that safe.  They assume one upstream credential per
   resource owner.

7.7.  What the Upstream Resource Sees

   The upstream resource sees one client, the broker.  It cannot tell
   which logical client or which instance caused a request, and it
   applies its rate limits and quotas to the credential.  Instances that
   share an upstream grant share those limits, and one can exhaust them
   for the others.  A broker SHOULD limit each logical client and each
   instance key separately.

   Attribution of a request to an instance exists only at the broker.  A
   broker SHOULD keep, for each request it sends upstream, the client
   identifier, the thumbprint of the key the token was bound to, any
   instance context, and the upstream grant identifier.  This document
   defines no format for that record.




Sweeney                    Expires 24 May 2027                 [Page 23]

Internet-Draft        OAuth Brokered Authorization         November 2026


7.8.  Withdrawal Is Not Immediate

   Withdrawal of a brokered authorization stops new tokens at once and
   takes effect at the broker within the limit stated under Section 6.6,
   and not sooner.  A request that the broker has already sent upstream
   is not recalled.

   Withdrawing the upstream grant itself is done at the upstream
   resource and is outside this document.

8.  Privacy Considerations

   The broker sees every request and every response it handles, in full,
   for every resource owner and client it serves.

   The upstream resource sees the broker and not the instance.  It does
   not learn which client or instance made a request unless the broker
   tells it.

   An upstream grant identifier is a stable value that stands for one
   resource owner at one upstream resource.  It is seen by the logical
   client and its instances.  It is specific to one logical client
   (Section 5), so two clients cannot correlate a resource owner by it.

11.  Open Issues

   *  Restricting a brokered authorization to some instances of the
      logical client, for example by attester, by tenant, or by a
      condition the resource owner sets (Section 7.2).

   *  An instance that starts a further instance of a different logical
      client.  This document covers only instances of the client the
      brokered authorization was made to.

   *  Client instances that authenticate with an assertion issued by
      their platform and not with a key of their own.

   *  A broker as the enforcement point for authorization details types
      defined elsewhere, such as that of [MISSION-RA].

   *  How a client learns the operation names a broker resource uses.

   *  The forwarding rules listed in Section 6.9, which are candidates
      for a companion document.

   *  Upstream resources that answer with a challenge for stronger
      authentication or for interactive consent.

   *  Evidence of each request sent upstream that a party other than the
      broker can check.

   *  Operation of the broker and its authorization server by separate
      parties.
